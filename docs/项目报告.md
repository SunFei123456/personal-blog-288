## 1. 需求分析

### 1.1 项目背景

随着互联网的发展，个人博客成为知识分享和个人品牌建设的重要平台。本项目旨在开发一个功能完善、界面美观的个人博客管理系统，支持多用户使用，实现文章的创建、编辑、发布和管理功能。

### 1.2 核心功能点

本系统围绕博客内容管理的核心需求，设计了六大功能模块。用户认证模块提供安全的身份验证机制，确保用户数据的隐私性；文章管理模块是系统的核心，支持完整的内容生命周期管理；分类和标签管理模块帮助用户对文章进行有效的组织和归类；内容展示模块负责将 Markdown 格式的文章渲染为美观的页面；后台管理模块则为管理员提供了系统级的控制能力。

| 功能模块 | 功能描述 |
|---------|---------|
| **用户认证** | 用户注册、登录、登出，JWT Token 认证 |
| **文章管理** | 文章的创建、编辑、删除、发布/草稿状态切换 |
| **分类管理** | 文章分类的增删改查，用户独立维护 |
| **标签管理** | 文章标签的增删，支持多标签 |
| **内容展示** | Markdown 渲染、文章列表、详情页 |
| **后台管理** | 管理员控制台、用户管理、数据统计 |

### 1.3 用户角色

为了实现灵活的权限控制和功能隔离，系统采用了基于角色的访问控制（RBAC）模型。通过区分普通用户和管理员两种角色，系统能够在保证普通用户独立管理自己内容的同时，赋予管理员对整个平台的监管能力。这种设计既保护了用户的数据隐私，又确保了平台的可管理性。

系统支持两种用户角色：

1. **普通用户（User）**
   - 注册、登录系统
   - 管理自己的文章、分类、标签
   - 查看自己的文章列表

2. **管理员（Admin）**
   - 拥有普通用户所有权限
   - 查看系统统计数据
   - 管理所有用户的文章、分类、标签
   - 用户管理（查看、删除用户）

## 2. 概要设计

### 2.1 系统架构

本系统采用现代化的前后端分离架构，这种架构模式将用户界面与业务逻辑完全解耦，使得前端和后端可以独立开发、测试和部署。前端负责用户交互和页面渲染，后端专注于业务逻辑处理和数据管理，两者通过 RESTful API 进行通信。这种设计不仅提高了开发效率，还增强了系统的可维护性和可扩展性。

本系统采用前后端分离的 B/S 架构，分为三层：

- **表现层（Frontend）**：Vue3 + TypeScript + TailwindCSS
- **业务逻辑层（Backend API）**：FastAPI + Python
- **数据持久层（Database）**：MySQL 8.0

## 3. 数据库设计

数据库设计是系统开发的基础环节，良好的数据库设计能够确保数据的完整性、一致性和查询效率。本系统采用关系型数据库 MySQL 进行数据存储，通过合理的表结构设计和外键约束，建立了清晰的实体关系模型。

### 3.1 E-R 图

实体关系图（E-R 图）是数据库设计的重要工具，它直观地展示了系统中各实体之间的关联关系。本系统包含五个核心实体：用户、文章、分类、标签和文章标签关联表。用户与文章、分类、标签之间都是一对多的关系，表示一个用户可以拥有多篇文章、多个分类和多个标签。文章与分类是多对一的关系，每篇文章只能属于一个分类。文章与标签之间是多对多的关系，通过中间表 article_tags 来实现关联。

### 3.2 数据表结构

以下是系统中各数据表的详细结构设计。每个表都经过精心设计，包含了必要的字段、约束和索引，以确保数据的完整性和查询性能。

#### 3.2.1 用户表 (users)

用户表是系统的核心表之一，存储了所有用户的基本信息和认证数据。表中使用 password_hash 字段存储经过 bcrypt 加密的密码哈希值，确保用户密码的安全性。role 字段采用枚举类型，限定用户角色只能是 'user' 或 'admin'，从数据库层面保证了角色数据的有效性。

| 字段名 | 类型 | 约束 | 说明 |
|-------|------|------|------|
| id | INT | PRIMARY KEY, AUTO_INCREMENT | 用户ID |
| username | VARCHAR(50) | NOT NULL, UNIQUE | 用户名 |
| email | VARCHAR(100) | NOT NULL, UNIQUE | 邮箱 |
| password_hash | VARCHAR(255) | NOT NULL | 密码哈希 |
| avatar | VARCHAR(255) | NULL | 头像URL |
| role | ENUM('user','admin') | DEFAULT 'user' | 用户角色 |
| created_at | DATETIME | DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| updated_at | DATETIME | ON UPDATE CURRENT_TIMESTAMP | 更新时间 |

#### 3.2.2 文章表 (articles)

文章表是系统中数据量最大的表，存储了所有博客文章的内容和元数据。content 字段使用 TEXT 类型以支持长篇幅的 Markdown 内容。status 字段区分草稿和已发布状态，允许用户保存未完成的文章。view_count 字段用于统计文章的阅读量，为后续的数据分析提供支持。通过 user_id 和 category_id 外键，文章与用户和分类建立了关联关系。

| 字段名 | 类型 | 约束 | 说明 |
|-------|------|------|------|
| id | INT | PRIMARY KEY, AUTO_INCREMENT | 文章ID |
| title | VARCHAR(200) | NOT NULL | 文章标题 |
| content | TEXT | NOT NULL | 文章内容(Markdown) |
| summary | VARCHAR(500) | NULL | 文章摘要 |
| cover_image | VARCHAR(255) | NULL | 封面图URL |
| status | ENUM('draft','published') | DEFAULT 'draft' | 文章状态 |
| view_count | INT | DEFAULT 0 | 浏览量 |
| user_id | INT | FOREIGN KEY | 作者ID |
| category_id | INT | FOREIGN KEY | 分类ID |
| created_at | DATETIME | DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| updated_at | DATETIME | ON UPDATE CURRENT_TIMESTAMP | 更新时间 |

#### 3.2.3 分类表 (categories)

分类表用于存储文章的分类信息。每个用户可以创建自己的分类体系，通过 user_id 外键实现用户间分类的隔离。这种设计使得不同用户可以根据自己的需求自定义分类结构，互不干扰。

| 字段名 | 类型 | 约束 | 说明 |
|-------|------|------|------|
| id | INT | PRIMARY KEY, AUTO_INCREMENT | 分类ID |
| name | VARCHAR(50) | NOT NULL | 分类名称 |
| description | VARCHAR(255) | NULL | 分类描述 |
| user_id | INT | FOREIGN KEY | 所属用户ID |
| created_at | DATETIME | DEFAULT CURRENT_TIMESTAMP | 创建时间 |

#### 3.2.4 标签表 (tags)

标签表采用轻量级设计，仅包含标签名称和所属用户信息。与分类不同，标签提供了更灵活的文章组织方式，一篇文章可以关联多个标签，便于从不同维度对文章进行检索和归类。

| 字段名 | 类型 | 约束 | 说明 |
|-------|------|------|------|
| id | INT | PRIMARY KEY, AUTO_INCREMENT | 标签ID |
| name | VARCHAR(50) | NOT NULL | 标签名称 |
| user_id | INT | FOREIGN KEY | 所属用户ID |

#### 3.2.5 文章标签关联表 (article_tags)

文章标签关联表是实现文章与标签多对多关系的中间表。该表采用复合主键设计，由 article_id 和 tag_id 共同组成，既保证了关联关系的唯一性，又优化了查询性能。通过这个中间表，系统可以高效地查询某篇文章的所有标签，或者查询某个标签下的所有文章。

| 字段名 | 类型 | 约束 | 说明 |
|-------|------|------|------|
| article_id | INT | PRIMARY KEY, FOREIGN KEY | 文章ID |
| tag_id | INT | PRIMARY KEY, FOREIGN KEY | 标签ID |

## 5. 接口列表

本系统采用 RESTful API 设计规范，所有接口都遵循统一的 URL 命名规则和 HTTP 方法语义。API 使用 JSON 格式进行数据交换，并通过 JWT Token 实现身份认证。所有需要认证的接口都要求在请求头中携带有效的 Bearer Token。

### 5.1 核心 API 接口

下表列出了系统的核心 API 接口。这些接口覆盖了用户认证、文章管理、分类管理和标签管理等主要功能模块。每个接口都经过精心设计，遵循 RESTful 最佳实践，使用合适的 HTTP 方法表达操作语义。

| 序号 | 接口路径 | HTTP方法 | 功能描述 |
|-----|---------|---------|---------|
| 1 | /api/v1/auth/register | POST | 用户注册 |
| 2 | /api/v1/auth/login | POST | 用户登录 |
| 3 | /api/v1/auth/me | GET | 获取当前用户信息 |
| 4 | /api/v1/articles | GET | 获取文章列表 |
| 5 | /api/v1/articles | POST | 创建文章 |
| 6 | /api/v1/articles/{id} | GET | 获取文章详情 |
| 7 | /api/v1/articles/{id} | PUT | 更新文章 |
| 8 | /api/v1/articles/{id} | DELETE | 删除文章 |
| 9 | /api/v1/categories | GET | 获取分类列表 |
| 10 | /api/v1/tags | GET | 获取标签列表 |

### 8.2 遇到的主要问题及解决方法

#### 问题1：JWT Token 认证失败

**问题描述**：用户登录后刷新页面，Token 验证失败，被重定向到登录页。

**原因分析**：JWT 的 `sub` 字段要求必须是字符串类型，但代码中传入了整数类型的用户ID。

**解决方法**：
```python
# 修改前
access_token = create_access_token(data={"sub": user.id})

# 修改后
access_token = create_access_token(data={"sub": str(user.id)})
```

#### 问题2：CORS 跨域问题

**问题描述**：前端请求后端 API 时出现跨域错误。

**解决方法**：在 FastAPI 中配置 CORS 中间件：
```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5173"],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

#### 问题3：用户权限控制

**问题描述**：普通用户可以访问管理员专属页面。

**解决方法**：
1. 前端路由守卫添加权限检查
2. 后端 API 添加角色验证依赖
3. 菜单根据用户角色动态显示
